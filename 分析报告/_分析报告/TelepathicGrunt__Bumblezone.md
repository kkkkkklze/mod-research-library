## 3. 入口与注册

三端入口各自只做"配置 + 模块初始化 + `Bumblezone.init()` + 事件桥接"：`$N/neoforge/BumblezoneNeoForge.java:19-34`（`@Mod(MODID)`，先 `BzConfigHandler.setup`、`NeoForgeModuleInitializer.init()`、`Bumblezone.init()`，再注册 NeoForge 专有的 GLM/BIOME_MODIFIERS/ATTACHMENT_TYPES 三个 `DeferredRegister`）、`$N/neoforge/BumblezoneNeoForgeClient.java:12-22`、`$F/fabric/BumblezoneFabric.java:11-18`。

真正的装配表在 common：`$C/Bumblezone.java:126-209`。它先挂 40 多条事件监听，再逐个 `.init()` 注册表：

```java
public static void init() {
    BzTags.initTags();
    BzRegisterCommandsEvent.EVENT.addListener(BzCommands::registerCommand);
    BzPlayerPickupItemEvent.EVENT.addListener(BeeAggression::pickupItemAnger);
    BzEntityTravelingToDimensionEvent.EVENT.addListener(EntityTeleportationBackend::entityChangingDimension);
    ...
    BzItems.ITEMS.init();  BzBlocks.BLOCKS.init();  BzEntities.ENTITIES.init();   // :175,:176,:185
}
```

注册方式是 **自研 helper + 第三方库**：`$C/modinit/*.java` 共 35 个类，全部用 ResourcefulLib 的 `ResourcefulRegistries.create(BuiltInRegistries.X, MODID)` 得到 `ResourcefulRegistry<T>`，再 `register(name, supplier)` 拿 `RegistryEntry<T>`（例：`$C/modinit/BzItems.java:59,62`、`$C/modinit/BzDimension.java:20-26`）。注册数量：`ITEMS.register` 154 次、`BLOCKS.register` 79 次、`ENTITIES.register` 14 次、`FEATURES.register` 24 次、`STRUCTURE_PROCESSOR.register` 24 次、`STRUCTURES.register` 3 次。为什么不用 `DeferredRegister`：它跨不过 loader，而 `ResourcefulRegistry` 在 Fabric/NeoForge 上行为一致；只有 loader 专有注册表（attachment / biome modifier / GLM）落在 `$N/modinit/neoforge/`。

平台差异下沉到 `ServiceLoader`：`$C/services/PlatformService.java:46` 用 `GeneralUtils.loadService(PlatformService.class)`（实现见 `$C/utils/GeneralUtils.java:111-113`），两侧实现分别是 `$N/services/neoforge/NeoPlatformService.java` 与 `$F/services/fabric/FabricPlatformService.java`，声明文件 `META-INF/services/...PlatformService`、`...ClientPlatformService`、`...modcompat.TwilightForestCompatService` 在两个 loader 模块各一份（见 `git ls-files`，内容未验证）。最小差异例子：`createEntityType` 在 NeoForge 是 `.build(buildName)`（`$N/services/neoforge/NeoPlatformService.java:65-72`），Fabric 是 `.build()`（`$F/services/fabric/FabricPlatformService.java:73-80`）——common 里 `BzEntities.java:35-48` 因此完全不碰 builder。

事件总线订阅点：common 自造三种总线（`$C/events/base/`，各 1 个类）——`EventHandler<T>`（`:9-30`，`addListener`/`invoke` 顺序遍历）、`CancellableEventHandler<T>`（把 cancelled 作为参数链式传递）、`ReturnableEventHandler<T,R>`（后一个监听器看到前一个的返回值，用于 `InteractionResult`/挖掘速度这类"取最后有效值"语义）。`BzEntityHurtEvent.EVENT_LOWEST` / `BzPlayerItemUseOnBlockEvent.EVENT_HIGH` 这类常量名不是优先级，而是**同一时刻的不同事件对象**，由 loader 侧决定在原生事件的哪个阶段 invoke（`$N/neoforge/NeoForgeEventManager.java:287` 对 `EVENT_LOWEST`，`:273,280` 对同一 `BzProjectileHitEvent` 的 HIGH/普通两次 invoke）。NeoForge 侧一个 478 行的 `NeoForgeEventManager.init(modEventBus, eventBus)` 把原生事件转发成 Bz 事件（如 `:178` `BzSetupEvent.EVENT.invoke(new BzSetupEvent(event::enqueueWork))`）；Fabric 侧 `FabricEventManager` 用 Fabric API 能给的点转发（`:156,161,185-196`），Fabric API 没给的（living hurt / block break / death）由 `$F/mixin/fabric/entity/LivingEntityMixin.java:45-58`、`$F/mixin/fabric/entity/PlayerMixin.java:70-71` 等 mixin 手动 invoke。

客户端入口同样只有一行转发：`$F/client/fabric/BumblezoneFabricClient.java:11` 与 `$N/neoforge/BumblezoneNeoForgeClient.java:17` 都调 `BumblezoneClient.init()`，实体注册/雾/着色器/按键全部由 common 的 `$C/client/BumblezoneClient.java:146-165` 挂到自己的 `BzRegister*Event` 上（`BzRegisterParticleEvent`、`BzRegisterEntityRenderersEvent`、`BzRegisterDimensionEffectsEvent`、`BzRegisterShaderEvent`、`BzRegisterMenuScreenEvent`…，共 17 个 client 事件类在 `$C/events/client/`）。`:147` 那行 `FactoryManager.register(rl(MODID,"connected"), ConnectedBlockModel.FACTORY)` 是 ResourcefulLib 的模型工厂注册，配合 `$C/client/blocks/ConnectedBlockModel.java` 做"相邻方块连接材质"，这样连方块外观方案都不必写 loader 代码。

## 4. 核心系统

**4.1 秘境维度：怎么进、怎么出、数据怎么跟着走**

维度本体是数据驱动的：`data/the_bumblezone/dimension/the_bumblezone.json` + `dimension_type/the_bumblezone.json`（存在于 `git ls-files`，内容未验证），代码只提供 `ResourceKey`（`$C/modinit/BzDimension.java:18`）和被 JSON 引用的 `chunk_generator` / `biome_source` / `density_function` 三个 codec（`:20-26`）。

入口不是原版 portal 框架，也**不是自定义 PortalShape**，而是"投掷物/右键/活塞把实体推进蜂箱 → 排队传送"。触发面在 `$C/entities/teleportation/`：`EntityTeleportationHookup.java:178-215`（`runTeleportProjectileImpact`：命中点是蜂箱、或命中点附近/沿速度方向一格附近有蜂箱，再检查蜂巢下方方块是否合规）、`ItemUseOnBlock.java`（右键类道具）、`runPistonPushed`（被活塞推入，见 `$C/modcompat/BumblezoneAPI.java` 对应导出）。哪些方块算蜂巢由标签 + 配置决定：`$C/entities/teleportation/EntityTeleportationBackend.java:227-247`（`FORCED_ALLOWED_TELEPORTABLE_BLOCK` 优先、`DISALLOWED_TELEPORTABLE_BEEHIVE` 否决、原版 BEEHIVES 或 `allowTeleportationWithModdedBeehives` + `ModCompat.HIVE_TELEPORT_COMPATS` 扩展）。

执行流程是"队列 + 异步选址 + 主线程收尾"：`BzWorldSavedData.queueEntityToTeleport`（`:74-78`）把 (entity, 目标维度) 入队；每 tick 由 `tick(ServerLevel)`（`:94-190`）消费，选址丢给线程池 `ThreadExecutor.dimensionDestinationSearch`（`$C/utils/ThreadExecutor.java:164-177`），完成后 `.thenOnServerThread(...)`（`:243-246`，内部 `server.submit`）把结果回投主线程；`EntityTeleportationBackend.getBzCoordinate`（`:88-145`）按 `dimensionType().coordinateScale()` 换算坐标、在 32 格内做螺旋搜索两处空气（`:157-215`），并在"下方一路是空气"时补一块 HONEYCOMB 防坠（`:130-136`）。出口是对称的：`EntityTeleportationHookup.java:104-146` 在 y < -2 或 y > 255 时钳位 + `teleportOutOfBz`，目的地取自实体身上的 `EntityPosAndDimModule`（`:148-175`），取不到则回落到配置 `defaultDimension`。

跨维度持久化：进维度那一刻把来处写进实体附件——`EntityTeleportationBackend.entityChangingDimension`（`:249-277`）在 `BzEntityTravelingToDimensionEvent` 里存 `nonBZDim/nonBZPos`；`$C/modules/EntityPosAndDimModule.java:13-17` 用 Codec 定义，`nonBZDimension` 的默认值直接来自配置的 `defaultDimension`（于是改配置能救回老存档的孤儿实体）。玩家进度（是否蜂 Essence、各类计数器）走 4.4 的 Module。移动本身是**手写重生包**：`BzWorldSavedData.java:313-329` 发 `ClientboundRespawnPacket` + `teleportTo` 再补发 difficulty/experience/abilities/effects/levelInfo/permission/allPlayerInfo 七个包，并给 SLOW_FALLING 20 tick。非玩家实体走 `type().create(destination)` + `restoreFrom` + `addDuringTeleport`（`:340-346`），骑乘关系用递归 `teleportEntityAndAssignToVehicle` 重建（`:293-351`）。

**4.2 世界生成：数据驱动 + 明确的性能取舍**

`$C/worldgen/dimension/BzChunkGenerator.java` 继承 `NoiseBasedChunkGenerator`（需要 `accesstransformer.cfg` 把 `doCreateBiomes/doFill/createNoiseChunk` 放开，见 `common/src/main/resources/META-INF/accesstransformer.cfg:4-7` 与 `the_bumblezone.accesswidener:5-8`）。关键设计：它往 NoiseRouter 里塞一个自定义密度函数 `BiomeNoise`（`:121-152`，按列采样"群系 influences 地形高度"），构造时用 `NoiseGeneratorSettingsAccessor` 把 settings 里的 router 整个换掉（`:101-112`）；但 codec 序列化出来的 `BiomeNoise` 只有 null 引用，于是靠 `$C/mixin/world/NoiseChunkMixin.java:47-53` 的 `@ModifyReturnValue(method="wrapNew")` 在每个 NoiseChunk 创建时把它替换成持有本 chunk 的 biomeSource + 预建 `Climate.Sampler` 的实例。这是"自定义 DensityFunction 需要访问上下文对象"的标准解法，值得抄。

性能取舍集中在四处：① `globalFluidPicker` 被换成常量返回 sea 状态（`:116-118`），等于关掉含水层计算；② `applyCarvers` 覆写成空方法（`:296`），洞穴改由自己的 feature 做（`worldgen/features/HoneycombCaves.java` 等 24 个 feature）；③ `getBaseHeight/getBaseColumn` 不复用 chunk，而是现场 new 一个 `NoiseChunk(1, ...)` 只跑目标列（`:209-264`）；④ `doFill` 是手写的一份 vanilla 填充循环（`:298-357`），好处是能把 OCEAN_FLOOR_WG / WORLD_SURFACE_WG 两个 heightmap 从顶到底预置成 `BEEHIVE_BEESWAX`（`:304-309`）。群系侧 `doCreateBiomes` 把 y 强制成 0（`:167-169`）并用 `NoVerticalBlendBiomeManager`（`:277`）保证一列一个群系、不做垂直混合。

结构是重头：`$C/worldgen/structures/OptimizedJigsawManager.java`（578 行，源自 YUNG's Better Strongholds 的限量 jigsaw）用 `size` 限制拼图块数（`:196-207`），并用 `BoxOctree`（`$C/utils/BoxOctree.java`，183 行）做边界与相交判定：`withinBoundsButNotIntersectingChildren`（`:498-499`）保证新块不重叠、`boundaryContains/withinAnyBox`（`:405`）做快速拒绝。它对外暴露成一个**可被 datapack 使用的结构类型** `generic_optimized_structure`（`$C/worldgen/structures/GenericOptimizedStructure.java:34-45` 的 codec 有 `size`/`max_distance_from_center`/`valid_biome_radius_check`/`min_y_limit`/`disable_bound_checks`/`start_jigsaw_name`），另有 `pollinated_stream`、`honey_cave_room` 两个自定义结构（`$C/modinit/BzStructures.java:17-19`）。数据规模（`git ls-files` 计数，内容未读）：`data/the_bumblezone/**` 共 2,778 个文件（1,928 `.json` + 850 `.nbt`），其中 `structure/**` 850 个 `.nbt`（sempiternal_sanctum 一个结构占 412 块）、`worldgen/**` 573（template_pool 256 / processor_list 158 / placed_feature 57 / configured_feature 39 / structure 33 / structure_set 10 / biome 9 / density_function 6 / noise 4 / noise_settings 1）、`tags/**` 430、`bz_bee_queen_trades/**` 334。结构处理器 24 个注册在 `$C/modinit/BzProcessors.java`，用于把模板里的占位方块按群系/随机替换。群体刷蜂的性能开关：`$C/mixin/world/ServerWorldMixin.java:31-46` 每 21 tick 统计一次维度实体数，`BzGeneralConfigs.specialBeeSpawning` 打开时 `spawnOriginalMobs` 会把 CREATURE 列表里的原版 BEE 摘掉改由自建系统刷（`$C/worldgen/dimension/BzChunkGenerator.java:400-402`）。

**4.3 生物与 AI：全部走原版 Goal 分层，不用 Brain/Schedule**

实测 `grep -rln "MemoryModuleType|SensorType|Brain<" common/src/main/java` 命中 0 个文件——本 mod 完全不用 1.19+ 的 Brain 系统。AI 分层靠 `goalSelector.addGoal(优先级, goal)`：`$C/entities/mobs/RootminEntity.java:343-350` 起排了 0-8 层（FloatGoal → RootminAntiGoal → RootminAngryGoal → RootminEmbarrassedCurseGoal → RootminCuriosityGoal → RootminHiddenGoal → RootminAvoidEntityGoal(..., BzTags.ROOTMIN_PANIC_AVOID, ...) → RootminHideGoal），`$C/entities/goals/` 共 24 个 goal，按前缀分组：Rootmin* 10、HoneySlime* 7、Beehemoth* 3、BeeQueen* 2、以及给原版蜜蜂补的 `BeeFlowerHeadwearTemptGoal`。

形态切换用枚举 + 实体数据：`$C/entities/mobs/BeeQueenState.java:10-21`（`ByIdMap.continuous` + `ByteBufCodecs.idMapper` 的 `STREAM_CODEC`），三个自定义 serializer 在 `$C/Bumblezone.java:229-233` 注册（queen_pose / rootmin_pose / cosmic_crystal_state）。

## 7. 值得学的 5 条

1. `common/src/main/java/com/telepathicgrunt/the_bumblezone/modules/registry/ModuleRegistry.java:16-25` + `neoforge/src/main/java/com/telepathicgrunt/the_bumblezone/modules/neoforge/NeoForgeModuleInitializer.java:22-63` + `fabric/src/main/java/com/telepathicgrunt/the_bumblezone/modules/fabric/FabricModuleInitializer.java:12-35`：一份 `ModuleHolder(id, codec, factory)` 声明，两处落成各 loader 的持久化附件（NeoForge `AttachmentType` / Fabric `AttachmentRegistry`），"死亡是否复制"作为声明参数。为什么值得抄：它把"存档字段"变成数据声明，加字段不动存储层，比 Cardinal Components 之类的外部依赖轻得多——求仙问道的境界/灵根数据可直接套这个形状。

## 8. 公开 API

它确实对外暴露扩展点，且明确承诺路径稳定：`$C/modcompat/BumblezoneAPI.java:27-32` 的类注释写着"给想调 Bumblezone 方法又不想被重构打坏的 mod 用"。内容分四类（均为 `public static`）：维度进出（`MOD_DIMENSION_ID:37`、`teleportOutOfBz:45`、`queueEntityForTeleportingToBumblezone:117`、`queueEntityForTeleportingOutOfBumblezone:125`）、把原版"末影珍珠式入口"接给别人（`runEnderpearlImpact` 两个重载 `:54,63`、`runItemUseOn:72`、`runGenericTeleport:81`、`runPistonPushed:88`）、成就触发（`triggerEnderPearlAdvancement:95` 等 4 个）、以及查询能力（`playerHasBeeEssence:133`、`getCombCutterLevelForItem:147`、`getCombCutterLevelForPlayer:154`）。注释里点名被 Requiem / Traveler's Anchor 一类 mod 使用。此外：`$C/modcompat/ModCompat.java:26-50` + `ModChecker.java:13-26` 的 14 个 compat 槽位是"别的蜂系 mod 想被蜂巢/刷怪/穿戴识别"时的注册面；`$C/Bumblezone.java:266-269` 的 `MOD_COMPAT_DATAPACKS` 允许外部往条件 datapack 列表里加内容；`$C/events/**` 的 `Bz*Event.EVENT.addListener` 事实上是公开钩子（谁都能监听/发），这是它比原版 Forge 事件更好旁路的地方；世界生成侧 `generic_optimized_structure` / `pollinated_stream` / `honey_cave_room` 三个 `StructureType`（`$C/modinit/BzStructures.java:17-19`）以及 `chunk_generator` / `biome_source` / `density_function` 三个 codec（`$C/modinit/BzDimension.java:24-26`）允许别人的 datapack 直接引用。工程面：三端都 publish maven（含 `withSourcesJar`，`build.gradle:156`），外部 mod 可 compileOnly `com.telepathicgrunt:the_bumblezone:7.16.0+1.21.1-neoforge`。未做未验证：`fabric.mod.json` 里是否声明 `entrypoints`/`depends` 之外还导出 API 模块，本地缺文件无法核对。
