# Modular Golems 源码分析报告

- 仓库: https://github.com/Minecraft-LightLand/ModularGolems（本地检出 `源码库/_参考仓库/_bulk/Minecraft-LightLand__ModularGolems`，分支 `1.20`，HEAD `c68eaad 2.7.1`）
- 路径缩写：下文 `…/` = `src/main/java/dev/xkmc/modulargolems/`；`init/…`、`content/…` 等均在 `…/` 之下。
- 先说一件最容易误判的事实：**这个 mod 完全不识别方块结构**。它没有"摆 4 个铁块 + 一个头 → 变傀儡"的逻辑，也没有任何方块实体（`content/block/` 只有 `TableBlock.java`，59 行，无 BE）。傀儡的"形状"活在**合成表的 shaped pattern** 与**物品 NBT 的部件列表**里，实体只在玩家右键放置 holder 物品那一刻被创建。对想看"多块拼傀儡"的读者，本仓库的价值不在扫描算法，而在"部件 → 属性 → 行为"的组合求值管线与傀儡的操作/绑定层。

## 3. 入口与注册

入口 `…/init/ModularGolems.java`：

```java
@Mod(ModularGolems.MODID)
@Mod.EventBusSubscriber(modid = ModularGolems.MODID, bus = Mod.EventBusSubscriber.Bus.MOD)
public class ModularGolems {
    public static final String MODID = "modulargolems";                                        // :56
    public static final L2Registrate REGISTRATE = new L2Registrate(MODID);                     // :58
    public static final IEventBus MOD_BUS = FMLJavaModLoadingContext.get().getModEventBus();   // :59
    public static final PacketHandlerWithConfig HANDLER = new PacketHandlerWithConfig(
            new ResourceLocation(MODID, "main"), 5, e -> e.create(ConfigSyncToClient.class, ...)); // :61-79
    public static final ConfigTypeEntry<GolemPartConfig> PARTS = new ConfigTypeEntry<>(HANDLER, "parts", ...);      // :81
    public static final ConfigTypeEntry<GolemMaterialConfig> MATERIALS = new ConfigTypeEntry<>(HANDLER, "materials", ...); // :83
    public ModularGolems() { registerRegistrates(); }                                          // :102-104

```

注册方式**不是 DeferredRegister，而是 Registrate**（`L2Registrate` 是 xkmc 对 Registrate 的子类封装）。构造函数里 `registerRegistrates()`（:86-100）只是按顺序 touch 各注册类的静态字段，靠静态初始化落地：`GolemItems.register()`、`GolemTypes.register()`、`GolemMiscs`、`GolemMiscEntities`、`GolemModifiers`、`MGConfig.init()`、`GolemModes.register()`、`GolemConfigStorage.register()`、`CurioCompatRegistry.register()`，并向 l2damagetracker 注册两个攻击监听（:97-98）。注意 `GolemTypes.register()`（`init/registrate/GolemTypes.java:149`）与 `GolemModes.register()`（`content/entity/mode/GolemModes.java:38`）**函数体是空的**——"register" 这个动词在本 mod 里等价于"让类被加载"。同一套模式还用来创建**自定义 Forge 注册表**：`REGISTRATE.newRegistry("modifier", …)`、`"stat_type"`、`"golem_type"`（`GolemTypes.java:37-39`），傀儡种类、属性项、修饰符都走自己的 IForgeRegistry，从而获得 `.getRegistryName()`、datagen 的 lang 生成与遍历能力。

事件订阅点全部用 `@Mod.EventBusSubscriber` 静态类，分三处：MOD 总线上 `ModularGolems`（`FMLCommonSetupEvent` :111、`GatherDataEvent` :122、`EntityAttributeModificationEvent` :106 空实现）与 `init/GolemClient.java`（`Dist.CLIENT`，:44）；FORGE 总线上 `events/ModifierEventListeners.java:34`（伤害/爆炸/能力挂载）、`events/GolemEventListeners.java:25`（装备槽判定）、`events/CraftEventListeners.java`、`events/GolemClientEventListeners.java`、`content/item/golem/ClientHolderManager.java:19`（客户端 tick 清缓存），以及各 compat 的 `*Dispatch` 在自己的构造里 `MinecraftForge.EVENT_BUS.register(XxxDispatch.class)`（如 `compat/materials/botania/BotDispatch.java:19`）。commonSetup 里用 `event.enqueueWork` 做发射器行为、武器表、快捷栏绑定（`ModularGolems.java:112-119`）。

## 4. 核心系统

### 4.1 装配：合成格就是"结构模板"，实体化点在物品右键

- 数据表示：傀儡的成品是一个 `GolemHolder` 物品（`content/item/golem/GolemHolder.java`，注册于 `init/registrate/GolemItems.java:315`），NBT 由 7 个约定 key 组成（:69-75）：`golem_materials` = `[{part: 物品RL, material: 材料RL}]` 有序列表（顺序 = `IGolemPart.ordinal()`）、`golem_upgrades`（字符串列表）、`golem_entity`（召回后塞回的完整实体 NBT）、`golem_equipments`、`golem_icon`、`golem_config`（绑定卡，见 4.4）、`golem_display`（纯展示血条）。
- 形状在哪里：三种傀儡各一条组装配方，形如 `"ABA" + " L "`（大傀儡，两臂 + 身体 + 腿）、`"A"+"B"+"C"`（人形，从上到下 身体/手臂/腿）、`"A"+"B"`（狗），见 `init/data/RecipeGen.java:127-133`、`:166-172`、`:198-203`。这些是 **datagen 产出的 JSON 配方**，类型为自定义 serializer `GolemMiscs.ASSEMBLE`（`init/registrate/GolemMiscs.java:34-35`），配方类 `content/recipe/GolemAssembleRecipe.java`：`matches` 在标准 shaped 匹配之上追加"每个 GolemPart 必须已注入材料"的检查（:22-35），`assemble` 把网格内每个部件的材料写进结果 holder（:38-47）。换件用 `GolemReplaceRecipe`（pattern 形如 `"PH"`/`"HP"`，`RecipeGen.java:135-161`），它在 `assemble` 里读 holder + 新部件后重建材料列表并拒绝剩余槽位为负的结果（`content/recipe/GolemReplaceRecipe.java:31-46`）。
- 触发时机：**没有任何 tick 轮询、没有方块扫描、没有放置回调**。玩家右键方块或右键生物时 `GolemHolder.onItemUseFirst`（:436-459）/ `interactLivingEntity`（:413-428）计算出生点（碰撞盒为空则原位，否则点面相邻格）后调 `summon`（:474-524）。`summon` 只在服务端分支里 `type.create(level, tag)` → `updateAttributes(materials, upgrades, ownerUuid)` → `setPos`（用 `level.findFreePosition` 挤进空间，:461-472）→ `initMode(player)` → `addFreshEntity`，然后 `stack.removeTagKey(KEY_ENTITY); stack.shrink(1)`——即"物品变实体"是一次性的、由玩家输入驱动。
- 反向转换：`AbstractGolemEntity.toItem(player)`（:290-300）记位置 → `GolemHolder.setEntity(entity)`（:179-210，把材料/升级/整份实体 NBT/血量写回物品）→ `discard()`。空手右键傀儡即可召回由 `mobInteractImpl`（:244-266）配合配置项 `MGConfig.COMMON.barehandRetrieve` 完成。
- 升级槽是"物品 NBT 的视图"，不是真实容器：`content/menu/table/GolemUpgradeItemHandler.java:18` 直接实现 `IItemHandlerModifiable`，把 holder 的 `golem_upgrades` 列表当成一个可变槽位组，容量由 `GolemHolder.getRemaining(mats, upgrades)` 算出（`content/item/golem/GolemHolder.java:602-621`：基础槽数来自傀儡类型或 `MGConfig.COMMON.*GolemSlot`，每装一个 `UpgradeItem` 减 1，再由 modifier 的 `addSlot` 加回），插入前先 `getRemaining < 0` 拒绝（`GolemUpgradeItemHandler.java:76`、`:90`）。菜单侧因此只需要 1 格真容器：`content/menu/table/GolemUpgradeMenu.java:33-40` 用 `BaseContainer<>(1, e)` + 两个 `DataSlot.shared(handler.data, 0/1)` 当"页码/最大页"，靠 `clickMenuButton`（:53-70）翻页，槽位由贴图 `sprite.getSlot("upgrades", …)` 批量生成。同一 `handler` 还支持"一个升级只吃 1 个物品"的语义（`quickMoveStack` :73-99 用 `copyWithCount(1)`）。这是"配置类 GUI 不落地实体容器"的干净写法，代价是要自己处理 `slotsChanged → setHolder` 的重绑（:47-51）。
- 拆解/融合（`content/menu/table/GolemDisintegrateMenu.java`，389 行）走的是同一思路的反向：把 holder 拆回部件与升级物品，配合 `init/loot/MGGLMGen.java` 的 `slicing` global loot modifier（序列化器注册于 `init/registrate/GolemMiscs.java:74-79`）从怪物掉落中直接产出升级件。
- 方块实体/实体转换点：**不存在方块实体层**，物品↔实体直接互转。`content/block/TableBlock.java` 只是菜单载体（`getMenuProvider` :42-45 用 `SimpleMenuProvider` 打开 `GolemUpgradeMenu`，无 BE、无朝向逻辑、无红石）。菜单也可脱离方块打开：`ModularGolems.java:116-118` 用 l2screentracker 的 `DefaultQuickAccessActions.quickAccess(...)` 把 `GolemUpgradeMenu::createFloating` 绑到快捷栏物品上。

### 4.2 部件 → 属性：三级乘算 + BASE/ADD/PERCENT 折叠

求值发生在**每一次 `updateAttributes` 调用**（组装召唤、读档 `readAdditionalSaveData` :542、出生包 `readSpawnData` :558、菜单里换件之后），不在 tick 里。三段式：

1. 单部件解析：`GolemPart.parseMaterial(材料RL)`（`content/item/golem/GolemPart.java:72-90`）＝ 材料原始值 `GolemMaterialConfig.stats[mat]` × **部件过滤器** `GolemPartConfig.filters[part][StatFilterType]` × **傀儡类型放大** `GolemPartConfig.magnifiers[golemType][statType]`，过滤后为 0 的项丢弃；同一函数顺手筛掉不允许挂在该部件上的 modifier（`k.canExistOn(this)`，:85）。过滤器语义见 `init/data/MGConfigGen.java:68-80`：身体吃 50% 血量/30% 质量但 0% 攻击，手臂吃 50% 攻击……这就是"哪个部件管哪类属性"的全部真相。
2. 汇总：`GolemMaterial.collectAttributes(list, upgrades)`（`content/config/GolemMaterial.java:31-90`）。按 `TreeSet<GolemStatType>`（注册名序，`GolemStatType.java:116-119`）保证顺序稳定，先把每个 Attribute 的每个 `Kind` 分别累加（:48-51），再折叠：只有 BASE 时才做 `(BASE + ADD) * (1 + PERCENT)`（:78-87）；只有 ADD 或只有 PERCENT 时直接以该项作为最终值返回（:59-76），由 `applyToEntity` 决定怎么写（`GolemStatType.java:84-92`：BASE 覆盖、ADD/PERCENT 基于当前 `getValue()` 再乘/加）。属性型 modifier（`AttributeGolemModifier`）在这一步也被折算进同一张表（:39-45）。
3. 落盘到实体：`AbstractGolemEntity.updateAttributes`（:165-196）先**把该实体所有已注册属性重置为 `DefaultAttributes.getSupplier(type)` 的基线**（:188-193 遍历 `ForgeRegistries.ATTRIBUTES`），再 `GolemMaterial.addAttributes`（`GolemMaterial.java:106-116`）叠加，最后 `refreshDimensions()`。同时 :169-187 计算 `modifiers`、`golemFlags`（由 modifier 的 `onRegisterFlag` 填）、按需换水生 `moveControl`/`navigation`、服务端重挂 modifier 提供的 Goal（用 `modifierGoals` 记录以便下次全量摘除）。
- 跨端：`materials`/`upgrades`/`modifiers`/`golemFlags`/`owner`/`leader` 全部标了 `@SerialClass.SerialField(toClient = true)`（`AbstractGolemEntity.java:127-137`），由 `writeSpawnData/readSpawnData`（:551-562）用 l2serial 的 `PacketCodec` 一次性反射写进实体出生包，客户端收到后**重新跑一遍 updateAttributes**——所以属性求值是两端各自算的同一函数，不需要额外同步属性值。tooltip 里的属性表则由 `GolemHolder.appendHoverText`（:338-410）在客户端用同一 `collectAttributes` 现算，因此"物品预览 = 实体真值"天然一致。

### 4.3 Modifier：注册表化的行为插件 + 一次性事件分发

`content/modifier/base/GolemModifier.java` 是一个继承自定义注册表条目（`NamedEntry<GolemModifier>`，:34-46）的**开放钩子类**，声明约 20 个空方法：`onGolemSpawn`、`onRegisterFlag`、`onRegisterGoals`、`onAiStep`、`onClientTick`、`onAttackTarget/onHurtTarget/onAttacked/onHurt/onDamaged`、`onKillTarget`、`onHealTick/onHealPre/onHealPost`、`isImmuneTo`、`addSlot`、`interact`、`handleEvent`、`modifySource`（:75-194）。等级由 `collectModifiers` 求和并 `Math.min(maxLevel, …)` 截断（`GolemMaterial.java:97-104`）。分发方式很干净：`events/ModifierEventListeners.java` 订阅 Forge 原版生命周期事件，命中 `AbstractGolemEntity` 就 `getModifiersExtended().forEach(k -> k.onXxx(...))`（:37-93）。
- 同一个类里还集中了几件"没做 mixin 也能改原版行为"的样板：爆炸剔除（:96-123，只保留可攻击目标并丢掉落物）、"傀儡抢仇恨"（:125-148，扫 `NearestAttackableTargetGoal` 找出打 IronGolem 的那条，复制优先级换成 `AbstractGolemEntity`——这正是 AT 暴露 `targetType/randomInterval/mustSee/mustReach` 四个字段的唯一用途）、掉落物吸附（:150-160，`event.getDrops().forEach(moveTo)`）、`EntityMobGriefingEvent` 返回 DENY（:183-189）。`getModifiersExtended()`（`AbstractGolemEntity.java:214-225`）在缓存的 `modifiers` 上临时叠加装备提供的 modifier，属于"每帧合成、不污染基准"的做法。
- 装备侧的另一个入口：物品实现 `IGolemModifierItem.getModifier(stack, entity)`，与 `getModifiers()`（纯材料+升级）区分开，保证 `updateAttributes` 的重算幂等。

### 4.4 指令与绑定：Level 能力 + (玩家UUID, 颜色) 的 16 格配置 + 心跳同步

- 服务端存储：`AttachCapabilitiesEvent<Level>` 里**只给主世界挂一个能力**（`events/ModifierEventListeners.java:162-170`），provider 是 `content/capability/GolemConfigCapability.java`（`ICapabilitySerializable<CompoundTag>`，用 `TagCodec` 反射序列化，:38-46）。能力对象 `GolemConfigStorage`（`content/capability/GolemConfigStorage.java`）内部两张表：`HashMap<UUID, GolemConfigEntry[16]>`（:47，下标 = 16 种染料色）与 `HashMap<UUID, GolemTracker>`（:49）。取用时用 `LAST_LEVEL/LAST_CACHE` 静态缓存跨维度指向 overworld（:24-33）——**全服傀儡配置是一份主世界存档里的全局表**。
- 实体侧只存 5 个 synched 值（2 个定位配置的 + 3 个行为相关的）：`CONFIG_ID`、`CONFIG_COLOR`、`DATA_MODE`、`GUARD_POS`、`PATROL_STAGE`（`AbstractGolemEntity.java:877-879`、:831-832），`getConfigEntry` 拿它们去查表（:885-900）。绑定物品 = `content/item/card/ConfigCard.java`：NBT 存 owner UUID（:38-43）+ `DyeColor`（:76-84），`getFilter(player)` 返回"这只傀儡是否戴这张卡"的谓词（:58-70），所有魔杖命令都先过它（`CommandWandItem.java:85`、`RetrievalWandItem.java:55`）。因此"一支wand指挥一队傀儡"零额外结构。
- `GolemConfigEntry`（`content/capability/GolemConfigEntry.java`）＝ 一份可编辑的策略：`defaultMode`、`summonToPosition`、`locked`，加四个子配置 `pickupFilter`/`targetFilter`/`squadConfig`/`pathConfig`（:29-42）。菜单侧统一走 `GolemConfigEditor` 接口，每个 setter 结尾调 `sync()`（`content/capability/GolemConfigEditor.java:33-58`）。

## 5. 网络 / 数据驱动 / 配置 / datagen

- 网络：一个 `PacketHandlerWithConfig`（= l2serial `BasePacketHandler` 的 `SimpleChannel` 封装，channel `modulargolems:main`，协议号 5，`init/ModularGolems.java:61-79`），登记 **16 个包**：`ConfigSyncToClient`、`ConfigUpdateToServer`、`ConfigHeartBeatToServer`（配置三件套）、`TrackerSyncToClient`/`TrackerHeartBeatToServer`/`TrackerDeleteToServer`（台账三件套）、`ReforgeUpdatePacket`、`GuardedEntity.GuardedDataToClient`（血量）、`SetItemFilterToServer`、`OpenConfigMenuToServer`、`OpenEquipmentMenuToServer`、`OpenTableMenuToServer`、`DogSkillToServer`、`GolemSetModeToServer`、`SetMaidModelToServer`、`SetPlayerSkinToServer`。包类只需标 `@SerialClass` + 字段 `@SerialClass.SerialField` 并实现 `handle(NetworkEvent.Context)`（例：`content/capability/ConfigSyncToClient.java:54-79`、`content/menu/wheel/GolemSetModeToServer.java:10-33`）——**没有一处手写 encode/decode，也没有 1.20.1 的 `CustomPacketPayload`/`RegisterPayloadHandlersEvent`**（那是 1.20.4+/NeoForge 的路子）。实体包用 `NetworkHooks.getEntitySpawningPacket`（`AbstractGolemEntity.java:547-549`）+ `IEntityAdditionalSpawnData`。

## 7. 值得学的 5 条

1. `content/recipe/GolemAssembleRecipe.java:21-47` — 用自定义 `RecipeSerializer` 把"结构识别"外包给原版工作台/配方系统，`matches` 里加语义校验、`assemble` 里把输入转成结果 NBT。为什么值得抄：免费拿到配方同步、JEI 集成、advancement unlock（`init/data/RecipeGen.java:127-133`）、`/recipe` 指令与数据包覆盖，全部不用自己写网络和 UI。
2. `content/item/golem/GolemPart.java:72-90` + `content/config/GolemMaterial.java:31-90` — "材料值 × 部位过滤器 × 种类放大 → 按 BASE/ADD/PERCENT 折叠"的三级求值。为什么值得抄：它把"每个部位贡献什么"从硬编码降到两行数据（`init/data/MGConfigGen.java:68-80`），加部位/加灵根都不用碰实体代码，而且物品 tooltip 与实体属性共用同一个纯函数，天然不会出现"预览和真值不一致"。
3. `content/capability/SyncContainer.java:21-53` + `content/capability/GolemConfigStorage.java:24-32` — 把"每只傀儡的配置"集中到主世界能力的 `(owner, 16 色)` 表，再用 200/100 tick 的玩家登记 + 心跳做增量同步。为什么值得抄：一队傀儡共享一套指令，只有一份 NBT、一个包，不需要给每个实体加 synched data，也不会因为玩家没看就广播。
4. `content/entity/common/GuardedEntity.java:101-133, 231-332, 336-358` — 服务端权威血量 + `GuardedData(amount, baseline)` 的"动态削减/不可瞬回"模型，配一个只发给 tracking players 的小包。为什么值得抄：求仙问道里"法宝反噬/气血可回不可刷"这类需求，最省事的实现就是这种"重写 setHealth 为 final + baseline 限流"的骨架，而且它同时兼顾了 absorption 与 invulnerable 两段原版逻辑。
5. `content/client/override/ModelOverride.java:40-62` + `content/client/override/ModelOverrides.java:19-30` — 外观 = 一份手写 `MeshDefinition`（`content/client/armor/GolemEquipmentModels.java:31-61`）+ 逐部件换贴图 + `_emissive` 后缀探测（带 ResourceManager 查询缓存）。为什么值得抄：零动画引擎、零额外模型格式依赖就能做出"每块材料不一样"的傀儡；自发光靠约定后缀，数据包里放不放 PNG 即开关，且探测结果缓存了。

结论：给「求仙问道」造傀儡/阵图玩法

三条能直接搬的形状（都带本仓库出处）：

1. **阵图 = shaped 配方，不是方块扫描。** 把"阵眼 + 灵材摆位"编码成一条自定义 serializer 的 shaped 配方（照 `content/recipe/GolemAssembleRecipe.java:21-47` + `init/registrate/GolemMiscs.java:34-39` 的三件套：Recipe 类 / Builder（`content/recipe/GolemAssembleBuilder.java`）/ Serializer 注册），成品是一个"法器/傀儡胚"物品，右键才 `addFreshEntity`（`content/item/golem/GolemHolder.java:474-524`）。这样阵图形状全部落在数据包 JSON 里，策划可改，且自动获得 NEI/JEI 展示与进度解锁。若确实要"方块摆地上召唤"，本仓库**帮不上**——它没有这段代码。
2. **三段属性表 + 每次全量复位重算。** 结构照抄：材料表（RL → stat map）、部位表（Item → filter map）、种类表（golem_type → magnifier map），求值时"遍历全部注册属性写回 `DefaultAttributes` 基线 → 折叠后逐条 apply → refreshDimensions"（`content/entity/common/AbstractGolemEntity.java:188-196` + `content/config/GolemMaterial.java:106-116`）。配 "属性型 modifier" 与 "标志型 modifier" 两类分离（`content/modifier/base/AttributeGolemModifier.java` vs `content/modifier/base/SimpleFlagModifier.java`），你的"剑意/御剑等级"这类数值走前者，"能否穿墙/免疫火焰"走 `GolemFlags`（`content/entity/common/GolemFlags.java`，9 行 enum）。
3. **一份全局指令表 + 颜色分组 + 台账。** 用 `AttachCapabilitiesEvent<Level>` 挂在 overworld 的存储（`events/ModifierEventListeners.java:162-170`），键 `(玩家UUID, 16 色)`（`content/capability/GolemConfigStorage.java:47`），实体只存两个 synched 值；再加一个 `GolemTracker` 式的死亡/召回台账（`content/capability/GolemTracker.java:17-113`）给 UI 用。对"多剑飞剑 / 多傀儡同指令"是直接对口的形状。

两个会踩的坑：

1. **全量复位会吃掉别人的属性贡献，且求值点很多。** `AbstractGolemEntity.java:188-193` 把所有已注册属性的 base 重置后重算，`updateAttributes` 在召唤（`GolemHolder.java:483`、`:506`）、读档（`AbstractGolemEntity.java:542`）、客户端收出生包（:558）、换件（`GolemEquipUtil`/菜单）都会跑；带装备 modifier 的那部分则被刻意排除在缓存之外（`getModifiersExtended()`，:214-225）。后果：任何"别的系统给傀儡加的属性/永久 modifier"会在下次换件或重登时被抹掉（reforge modifier 就得手工在 holder NBT 里删，见 `GolemHolder.java:253-267`）。求仙问道若打算让"功法/丹药"也改傀儡属性，必须先决定谁持有 base，别学这种"我全量重建"。
2. **索引/反射式序列化 = 隐式的存档与协议契约。** (a) `GolemMode` 的 ID 是静态初始化顺序的下标（`content/entity/mode/GolemModes.java:12-28` 的 `id = LIST.size()`），这个 int 被写进 synched data（`AbstractGolemEntity.java:831`）、配置 `defaultMode`（`content/capability/GolemConfigEntry.java:29`）和命令包（`content/menu/wheel/GolemSetModeToServer.java:29-32` 还要 `mode < LIST.size()` 兜底）——中间插入或重排一个模式，老存档的傀儡行为会静默错位。(b) `@SerialField(toClient = true)` 字段直接反射进实体出生包与 `auto-serial` NBT（`AbstractGolemEntity.java:127-141`、`:527-545`、`:551-562`），字段改名/改类型即丢数据且不会编译报错。建议：状态类一律显式存 RL/字符串 key 并在读取处解引用，客户端同步走显式 codec，别把"字段顺序"当协议。（顺带一个成本坑：`GolemHolder.inventoryTick` 每 20 tick 为背包里每个 holder 物品重跑 `collectAttributes` + `collectModifiers`（`content/item/golem/GolemHolder.java:298-335`），客户端假实体缓存 >100 条就整体清空并 `LOGGER.error`（`content/item/golem/ClientHolderManager.java:44-49`）——大批量携带时是可见的 CPU/GC 抖动。）

## 8. 公开 API 与扩展点

本 mod 有明确的"给别人加傀儡内容"的三层扩展点，但没有版本稳定的 API 包（类不在 `api/` 下，也无 `@API` 注解），第三方要么编译期依赖它、要么走数据：

1. 数据层（无需依赖）：往 datapack 的 `<modid>_config` 目录放 JSON 即可新增材料/部件过滤/种类放大（`content/config/GolemMaterialConfig.java:27-41` 的四个 `@ConfigCollect` map，`MAP_COLLECT` 表示多包同键合并、`MAP_OVERWRITE` 表示覆盖），以及普通配方 JSON（自定义 serializer id `modulargolems:golem_assemble` / `golem_replace_part` / `golem_add_slot`，`init/registrate/GolemMiscs.java:34-39`）。
2. Java 内容层：`GolemModifier` 子类 + 自定义注册表 `GolemTypes.MODIFIERS`（`content/modifier/base/GolemModifier.java:34-46`、`init/registrate/GolemTypes.java:37`）；新傀儡种类 = `EntityType` + `IGolemPart` enum（`content/entity/metalgolem/MetalGolemPartType.java:15-36`，三个方法：`setupItemRender`/`getDesc`/`toItem`）+ `GolemType`（`content/core/GolemType.java:47-54`，构造即把自己登记进 ENTITY_TYPE→GolemType / GolemHolder / ModelProvider 三张表）+ `ModelProvider`（`content/core/ModelProvider.java`）+ `AbstractGolemRenderer` 子类；属性项 = `GolemStatType`（`init/registrate/GolemTypes.java:52-67` 展示"属性 × Kind × StatFilterType"的三元注册）。
3. 事件层：`events/event/` 下 21 个自定义 `Event`（`GolemEvent` 基类 :6-20；`GolemEquipItemEvent`/`GolemEquipEvent` 可裁定装备槽，被 `content/menu/equipment/EquipmentsMenu.java:123-142` 和 `events/GolemEventListeners.java:28-60` 消费；`GolemInfoEvent` 让 compat 往傀儡信息页加行，见 `compat/materials/botania/BotDispatch.java:39-44`；`GolemToOwnerEvent`/`GolemCollectInventoryEvent` 在 `AbstractGolemEntity.java:1269-1290` 作为可取消的扩展点）。
4. 第三方 mod 侧：`compat/materials/common/ModDispatch.java:18-49` 是内部兼容 SPI（`getDataGen`/`genRecipe`/`genLang`/`commonSetup`/`lateRegister`/`genLootModifier`），配 `compat/materials/common/ClientModDispatch.java` 做客户端侧分离——本仓库自用，但结构很适合作为"求仙问道如何优雅地写 20 个兼容"的模板：一个 `ModList.isLoaded` 开关 + 一个 Dispatch 子类 + 可选 ConfigGen，兼容代码永不进入主路径。
