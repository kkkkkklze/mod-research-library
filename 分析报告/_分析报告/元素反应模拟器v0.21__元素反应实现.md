## 0. 这个项目是什么

包内自带 `记录内容.txt`，是一份**《高等元素论》读书笔记**，明确列出参考源（NGA《高等元素论》ver1.6、《附录·冻结反应机制》、3.0 激化/绽放/燃烧、两个 B站视频），并写下了要实现与不实现的清单。程序就是把这份笔记里的模型**做成可交互模拟器**：两个队伍互相放技能，你能看到元素附着条、反应名、伤害数字与冷却。

作者自述的**未处理**清单（与代码实测一致）：
> 碎冰（"判断逻辑不一致 跳过"）、扩散（单目标跳过）、冰冻衰减（跳过）、破盾中的反应、岩结晶、草原核的超绽放/烈绽放、**元素反应间隔 3 次/2.5s 计时机制（略）**。

**实测确认**：`ElementalController.hitThreshold = 3` / `timeThreshold = 2.5f` 两个字段**声明后从未被引用**（全文件仅第 297/300 行两处）——ICD 确实没实现。

## 1. 数据模型

### 1.1 `ElementalType`（11 值，含 3 个"藏元素"）

```csharp
Pyro, Pyro_Ex,      // Pyro_Ex = 燃元素（燃烧产生的火）
Hydro, Cryo, Cryo_Ex, // Cryo_Ex = 冻元素（冻结产生）
Electro, Anemo, Geo,
Dendro, Dendro_Ex,  // Dendro_Ex = 激元素（原激化产生）
Null
```
`_Ex` 后缀就是高等元素论里的**藏元素/次级元素**：火↔燃、冰↔冻、草↔激。风/岩只有枚举，无任何行为实现（`Anemo`/`Geo` 在代码中零引用）。

### 1.2 `ReactionType`（15 值）

`Vaporize, Melt, Overload, Superconduct, ElectroCharged, Shattered, Swirl, Crystallize, Frozen, Catalyze, Spread, Aggravate, Burning, Budding, Null`
其中 **Shattered / Swirl / Crystallize 三个对应的方法体是空的**（见 §6），与笔记"跳过"一致。

### 1.3 `ElementalInfo`（附着单元）与衰减公式

```csharp
public ElementalType type;
public float intensity;   // 元素量
public float damping;     // 衰减速度（每秒）
public int index;         // 全局自增序号（用于判定同帧施加顺序）

damping = 0.8f * intensity / (7f + 2.5f * intensity);   // 通用公式
// 例外（3.0 规则）：
Dendro_Ex: damping = intensity / (6f + 5f * intensity); // 激元素
Cryo_Ex:   damping = 0.4f;                              // 冻元素固定 0.4/s
Pyro_Ex:   damping = 0f;                                // 燃元素不衰减
```
`index` 由静态 `counter` 自增，用于 `BehaviorElemental` 里判定"谁先施加"（决定谁作为反应的主元素）。

## 2. 元素生命周期（每帧 `Update`）

1. **冻元素加速衰减**：存在 `Cryo_Ex` 时 `frozenRate += 0.1/s`，否则 `frozenRate -= 0.2/s`（下限 0）；冻结状态下冻元素的衰减速度变成 `damping + frozenRate`——即**冻得越久掉得越快**（这是笔记里"冰冻衰减 麻烦 跳过"，但代码其实实现了一个简化版）。
2. **燃烧期间草/激不衰减**：若存在 `Pyro_Ex`，则 `Dendro`/`Dendro_Ex` 跳过衰减（它们此时是**燃料**而非附着）。
3. **归零移除**：逐帧收集 `intensity <= 0` 并移除，然后刷新 UI（`UIManager.UpdateElementalRecord`）与图标条（`RoleBuffer.UpdateBufferIcon`）。

## 3. 反应派发与优先级（核心）

### 3.1 入口流程

```csharp
EventListenerElementalReaction(addElemental)          // ElementalController:594
  ├─ ReactionOverlap(已有同类, 新元素)                  // 叠加判定，见 §5
  ├─ 按类型分发：BehaviorPyro / BehaviorElectro / BehaviorCryo / BehaviorHydro / BehaviorDendro
  └─ 若本轮没发生反应（元素未被消费）且字典里没有该元素：
        addElemental.intensity *= 0.8f;  附 着 折 扣
        elementalDic[type] = addElemental;
```
技能侧只有一处调用：`RoleController.EventListenerSkillHappened`（`:1571`）——对每个目标先写 `damageInfo = new DamageInfo(随机伤害, 元素类型, ReactionType.Null)`，再调 `EventListenerElementalReaction`，最后由 `RecieveAbilityValue` 结算 HP（见 §7）。

### 3.2 `BehaviorXxx` 的实际判定顺序（= 规则表）

| 施加元素 | 判定顺序（自上而下，命中即执行） | 对应笔记规律 |
|---|---|---|
| **火 Pyro** | 存在冻元素？→ 融化(藏冰) → 融化(冻)【不再判雷/水】<br>否则 → 融化(冰) → 超载(雷) → 蒸发(水)；最后 燃烧(激元素优先，其次草) | 规律三/四（冻元素优先、不足由冻元素补） |
| **雷 Electro** | 超激化(激元素) → 存在冻？→ 超导(藏冰)+超导(冻)<br>否则 → 超导(冰) → 超载(燃/火) → 感电(水)；最后 原激化(草) | 规律二/三 |
| **冰 Cryo** | 超载(雷) → 融化(燃/火) → 冻结(水) | — |
| **水 Hydro** | 蒸发(燃/火) → 冻结(冰) → 绽放(激/草) → 感电(雷) | — |
| **草 Dendro** | 蔓激化(激元素) → 原激化(雷) → 燃烧(燃/火) → 绽放(水) | 3.0 新增 |

每帧的持续型反应在 `BehaviorElemental()` 里轮询：激元素+水→绽放、雷+水→感电跳伤、存在燃元素→燃烧 tick。

### 3.3 藏元素的"双元素同时消耗"

`GetElementalEx(type, out elemental, out subElemental)`（`:363`）：当火/草同时有本体与 `_Ex` 时，**取元素量大的作为主元素、小的作为副元素**；主元素参与反应，副元素按反应消耗量 `num` 同步扣减（`subElemental.intensity -= num`）——这就是笔记里的"燃火反应机制 / 激草反应机制：两种同时进行消耗"。

## 4. 各反应的实现细节

| 反应 | 消耗比 | 伤害影响 | 代码位置 |
|---|---|---|---|
| **蒸发** | 水:火 = 1:0.5（水多时）或 1:2（水少时） | 后手为**水** → `number *= 1.5`；后手为**火** → `*= 2` | `:650-704` |
| **融化** | 火:冰 = 1:0.5 / 1:2（同上结构） | 后手为**火** → `*= 2`；后手为**冰** → `*= 1.5` | `:706-760` |
| **超载** | 1:1 互耗 | 无倍率；显示基数 `"2893"` | `:762-809` |
| **超导** | 1:1 互耗 | 无倍率；显示 `"723"` | `:811-840` |
| **感电** | **不消耗**（后手不残留机制的例外）：入队时给新元素打 0.8 折并保留双元素 | 每 **0.5 s** 跳一次，水/雷各 `-0.4`；显示 `"1736"` | `:842-865` |
| **冻结** | `min(水,冰)` 互耗 → 生成 `Cryo_Ex = 2×num`（若已有更大的冻元素则不覆盖） | 无 | `:875-889` |
| **原激化** | `min(雷,草)` 互耗 → 生成 `Dendro_Ex = num` | 无 | `:891-905` |
| **蔓激化** | 不消耗（消耗的是激元素，在反应 tick 中算） | `number += 1808`（固定加伤） | `:907-914` |
| **超激化** | 同上 | `number += 1663` | `:916-923` |
| **燃烧** | 建 `Pyro_Ex = 2.0`；若火元素 < 0.8 则**自动补火到 0.8**（"完全独立的自动补充弱火机制"） | 每 **0.25 s** tick：dendro/dendro_Ex 各 `-0.1` 作燃料，燃料耗尽 → 燃元素归零；显示 `"361"` | `:925-976` |
| **绽放** | 水:草 = 1:0.5（同蒸发结构） | 显示 `"2888"` + 生成草原核视觉（`ShowSeedDisplay`） | `:978-1026` |
| 碎冰 / 扩散 / 结晶 | — | **空方法** | `:646,867,871` |

**基数自洽性检查** ✓：笔记写"燃烧：1 单位草元素燃烧 8 次，倍率总和 = 1 次超载"，代码里 `361 × 8 = 2888`，而超载基数 `2893`、绽放 `2888`——数字对得上（2888 被同时用作绽放基数与"8 次燃烧之和"）。笔记的克制比 1 : 1.2 : 2.4 : 3 : 4（超导:扩散:感电:碎冰:超载）对应基数 723 : 868 : 1736 : 2170 : 2893，代码里出现了 723/1736/2893 三项。

## 5. 元素叠加（`ReactionOverlap`）——"选其多后打 8 折"

```csharp
if (e1.type == e2.type && e1.intensity < e2.intensity * 0.8f) {
    e1.intensity = e2.intensity * 0.8f;     // 新量大 → 旧量更新为新量的 0.8
    if (e1.type == Pyro) e1.damping = e2.damping;   // 火元素例外：衰减速度同步修改（3.0 规则）
    e2.intensity = 0f;                       // 新元素被"吸收"，不重复入队
    return true;
}
```
- 新量**不够大**（< 旧量×0.8）时保留旧附着、新元素按普通附着流程以 0.8 折扣入队；
- 火的 `damping` 会被同步更新（笔记："3.0 激元素/火元素 例外（衰减速度同步修改）"）——激元素的同步体现在 `ElementalInfo` 构造函数里对 `Dendro_Ex` 的专用公式。

## 6. 完整性与疑似问题（实测）

**未实现（空方法/未引用）**
1. `ReactionShattered` / `ReactionSwirl` / `ReactionCrystallize` 方法体为空（`:646,867,871`）。
2. `hitThreshold=3` / `timeThreshold=2.5f` 声明但**零引用** → 元素反应 ICD 未实现（与笔记一致）。
3. 超绽放/烈绽放（草原核反应）未实现；`Anemo`/`Geo` 类型无任何逻辑。

**疑似 bug / 不一致（按代码事实列出，供参考）**
1. **冰打雷走的是"超载"**：`BehaviorCryo` 里 `ReactionOverload(elementalDic[Electro], addElemental)`（`:499`），而 `BehaviorElectro` 里雷打冰走 `ReactionSuperconduct`（`:461`）——**同一对元素双向结果不同**（冰→雷 显示"超载"，雷→冰 显示"超导"）。
2. **冻结显示复用了 `ReactionType.Crystallize`**：`DisplayElementalReaction("冻结", ReactionType.Crystallize)`（`:886`）——但 `RoleDamage.DisplayElementalReaction` 的 switch 里没有 Crystallize 分支，颜色沿用上一次的值；同时"冻结"在类型层面被记为结晶。
3. **转化类反应的伤害不结算**：超载/超导/感电/燃烧/绽放只把基数数字**显示**出来（`DisplayElementalReaction("2893", …)` 传的是字符串），并不修改 `damageInfo.number`；而蒸发/融化（×1.5/×2）与激化（+1663/+1808）会真正进 HP 结算（`RecieveAbilityValue((int)damageInfo.number)`）。如果你想拿它当伤害计算器用，这一点要自己补。
4. 受击动画只在非玩家单位播放（`if (!isPlayer) roleAnimation.CharacterHit()`），是模拟器取向而非 bug。

## 7. 伤害与技能链路（顺带看清工程结构）

```
RoleSkillData (ScriptableObject)      // 每技能一份数据资产
  ├─ targetType / valueModifier(Positive|Negative) / valueRange(Vector2Int)
  ├─ cooldownTime / elementType / elementIntensity   ← 元素量与元素类型在这里配置
  └─ 技能序列 = Unity Timeline 资产（Dialogue/Signal 轨道），到点触发 SignalReceiver
        → RoleSkill.SignalReceiverSkillHappened()    // 取随机伤害 + new ElementalInfo(type, intensity)
        → UnityEvent<int, TargetType, ElementalInfo> eventSkillValueToTargets
        → RoleController.EventListenerSkillHappened()  // 每个目标: 写 damageInfo → 反应引擎 → 结算 HP
        → RoleHealth.ChangeHealth()
```
- 技能/冷却/动画全靠 **Unity Timeline + SignalReceiver** 编排（`RoleSkill`、`RoleAnimation`、`RoleSkillController.StartSkillCooldowns`），`GameManager` 用 `GameMode` 状态机（InitData/Intro/GamePrePlay/GamePlay/DialogueMoment/Waiting）驱动整场战斗，按键 1–4 切换自动施法。
- 展示层：`RoleDamage`（反应名/伤害数字 + 按反应类型上色，颜色表在 `GameManager.elementalColors[0..4]`）、`RoleBuffer`（8 个附着图标 + 3 个状态图标：燃烧/冻结/激化）、`UIElementalRecord`/`UIElementalbarBehaviour`（附着记录与条）——**要观察元素量变化，UI 已经是最好的可视化工具**。

## 8. 可借鉴到 mod 的设计（对我们的元素/状态系统）

1. **"元素量 + 衰减 + 藏元素"三件套的最小实现**：11 个枚举值 + 一个 `ElementalInfo(type, intensity, damping)` + 每帧 `intensity -= damping*dt` 就够了，藏元素用 `_Ex` 后缀同表存储——想做原神式附着，可以照抄这个结构（约 200 行核心逻辑）。
2. **把"反应优先级"写成显式的 `BehaviorXxx` 顺序表**，比在一个大 `switch` 里塞条件可读得多；笔记里的四条规律直接对应代码里的判定次序，容易核对。
3. **消耗比的统一写法**：蒸发/融化/绽放共用同一段"`A >= B*0.5` → 扣 B 全量 + A 半量；否则 A 全量 + B 双倍"的结构——用一个系数（0.5/2）覆盖了 1:2 与 1:1 两类配比。
4. **用 `index` 全局自增序号解决"同帧谁先"**：比时间戳简单，且天然支持"后手不残留"判定。
5. 若要在 MC 里复刻：这套逻辑与实体解耦（`Dictionary<ElementalType, ElementalInfo>` 挂在实体上），移植成一个 capability/attachment + 每 tick 衰减即可；反应发生处抛出事件供伤害/特效系统订阅。
